# Adding a module

1. Choose an immutable slug, semantic module version and new numeric C module ID. Do not renumber released IDs. Add prerequisites, objectives, explanation, examples, invariants, honest complexity, input schema, operation labels, default input to `content/modules.json`; author teaching slides/concepts in `content/curriculum.json` and distinct practice/recorded questions in their separate banks. Follow [lesson authoring](lessons.md). The registry version describes its schema, independently of the engine/module versions.
2. Implement portable C17 lifecycle logic in `engine/src/engine.c` (split into files as the engine grows). Extend `engine_start` validation and `engine_next` dispatch. State transitions must be bounded and deterministic. Do not execute an entire unbounded algorithm during initialization or one advancement. Current fixed capacity is 32 sequence values / 16 vertices; new modules must state their own limits.
3. Return typed events using `emit`. Use existing compare/swap/read/write/insert/delete/visit/enqueue/dequeue/pointer-update/relax/complete concepts when they fit. Add versioned extension payloads when needed; do not force unrelated topics through the array adapter. Add the TypeScript event type to `protocol.ts` and document it.
4. Annotate each emission site with a unique `/* @loc:module.operation */`. `scripts/extract-source.py` extracts that exact compiled file and maps annotations to line numbers. Never maintain a second pretend-C listing. Include new source files in the extractor/compiler if splitting the core.
5. Add an SVG adapter (or justify Canvas with measurements), preserving conceptual stable node/edge identities. No visualization should derive algorithm steps independently from C. Show relevant variables and meaningful counter semantics; educational example code has no execution highlights. Keep animation pace separate from algorithm complexity.
6. Extend native oracle/invariant tests and the native/Wasm fixture generator; include empty input, duplicates, invalid operations, boundary capacity, disconnected state where relevant, deterministic reset and cleanup. Add browser interaction tests and a replay check for mutation events. Run `scripts/check.sh` with Docker and Playwright installed. The native suite is the same C source compiled without browser glue.
7. Add an append-only Flyway migration for new topic/lesson/algorithm/version/question content. Never rewrite an applied migration. V1–V5 are retained; new changes use V6+. Preserve old revisions/options and attempt snapshots. Update backend engine-input validation for the new module ID and schema, and extend content/security/persistence tests.
8. Update the roadmap, curriculum table, API/event docs and release checklist. Mark a module functional only after actual C → Wasm worker → adapter execution and tests pass.

Each cloud task already has an isolated checkout. Use the existing checkout; do not create a worktree unless explicitly requested. No arbitrary user-submitted C compilation is supported.

Learning-only modules such as Foundations need no numeric C ID: register concept visuals and explanatory slides instead. Group related algorithms into coherent lessons; preserve all runtime experiment IDs. Update negative concept validation and the five-language example harnesses alongside new content.

For the next-module pattern, see [contracts and authoring](next-modules.md). Add runtime IDs without broad numeric graph predicates (graphs are IDs 11–14), provide optional typed snapshot fields, and update both server saved-input validation and browser validation. Independently compilable new example files live in `content/examples/next`; register all five languages in its metadata and add behavior assertions to `scripts/test-next-examples.py`. Test C against independent result oracles, then cross-target snapshots and replay. Keep the bounded worker/player/progress implementation shared. Never edit V1–V6 for future content changes: freeze generation inputs and introduce a new migration.
